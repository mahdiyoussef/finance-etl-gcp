# FinPulse architecture and design decisions

## Problem and scope

FinPulse models an invoice-to-cash workflow and its relationship to customer
support. The design separates immutable source history from curated analytical
facts and current-state views. This allows late files, duplicate deliveries,
replays, and status corrections without losing auditability.

## Logical layers

### Landing

Landing contains the original Kaggle files and synthetic ticket JSONL events.
Files are retained with a manifest and source lineage. Landing is not queried
directly by analysts.

### Raw

Raw tables preserve source-level fields, ingestion timestamps, and source-file
metadata. Raw data is append-oriented and is the first replay boundary.

### Staging

Staging applies types, normalizes status values, resolves source aliases, and
standardizes dates and amounts. Staging models should be inexpensive views.

### Core

Core contains business-grain facts and dimensions. `fct_invoices` is
incremental and uses `invoice_id` as its merge key. Ticket events remain
immutable; `tickets_latest` is derived from event order.

### Marts

Marts are business-facing tables for AR aging, DSO, invoice risk, support cost,
and SLA performance. They are the only layer intended for dashboard users.

## Local execution

```text
Kaggle CSVs
    -> Airflow download task
    -> batch streaming normalizer
    -> SQLite raw/core tables
    -> quality checks
    -> AR, DSO, risk, and support marts
```

The normalizer reads `train_invoices.csv` and `test_invoices.csv` in bounded
chunks. It does not create an intermediate combined CSV. Business keys are
loaded with `insert or ignore`, so Airflow retries are safe.

## GCP mapping

| Local implementation | GCP target |
|---|---|
| Local dataset directory | GCS landing bucket |
| SQLite raw tables | BigQuery raw dataset |
| `load_external_dataset` | Dataflow batch or BigQuery load job |
| `BatchLoader.build_marts` | dbt incremental models |
| Airflow DAG | Cloud Composer DAG |

The dataset contains customer and vendor attributes but does not contain
support-ticket events. Support events remain a separate streaming contract and
are generated by the local synthetic source until a licensed ticket source is
selected.

## Key design decisions

### Why append-only events?

Ticket events are retained as facts because current state alone cannot answer
when a ticket changed status, how long it remained open, or whether a late event
arrived after a dashboard refresh.

### Why bounded streaming?

The complete source is approximately 1.3 GB extracted. Combining the train and
test files would create another large disk and memory pressure point. The
normalizer reads rows and flushes bounded SQLite batches.

### Why Airflow?

The workflow contains ordered dependencies, retries, freshness checks, quality
gates, and backfills. Airflow expresses those dependencies explicitly and can
move from local execution to Cloud Composer without changing task semantics.

### Why dbt?

dbt provides versioned SQL, incremental models, source freshness, tests, model
lineage, and documentation. Python handles ingestion; dbt handles warehouse
transformation.

### Why Terraform?

Terraform makes datasets, buckets, IAM, budgets, Pub/Sub, and monitoring
reviewable and reproducible. Dev and prod are separated to reduce accidental
destructive changes.
